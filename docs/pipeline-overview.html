AutoFactory pipeline

Phase 1 runs in CI on each pull request and creates the release resources (flag, metrics, tests, review verdict). Phase 2 receives deploy notifications and runs the release using those resources. Hover a node for the mechanics.

Note: this diagram reflects the primary repo maintainer's current setup. The pipeline itself is modular and customizable — where it runs, which agent provider(s) and models execute the chain, and which CD system notifies Beacon are all swappable seams that can be extended to other platforms and providers as needed; the agents' instructions, graph, and permissions are configuration, not code.

Phase 1: PR → release resources

GitHub Action on pull_request. Six agents, resolved from LaunchDarkly AI Configs at run time, chained by an agent graph.

Step 1
Developer opens a PR
unflagged feature change
The PR contains the feature change with no flag wiring. Classification, flag creation, code wiring, metric instrumentation, and tests are added by the agents as commits on the PR branch.
→
Step 2
Action invokes AutoFactory
runs on the PR checkout
Reusable GitHub Action triggered on pull_request. The PR branch checkout is the agents' working directory.
  • The agent graph and each agent's instructions are resolved from LaunchDarkly AI Configs at run time. Prompts are config, not code.
  • The auto-factory-ai-provider flag selects the backend per run: anthropic, vega, or cursor (Cursor agents). Each agent's model is resolved from its AI Config and mapped to the provider's catalog.
  • The targeting context is a multi-context (service static + run = fresh UUID), so coding agents can A/B their model (Composer vs Sonnet) independently per run.
  • Per-agent tool capabilities (create_flag, create_metric, edit_files, write_manifest, and read-only grants like read_docs — LaunchDarkly docs as markdown — and query_graph) are declared on the graph's edges.
  • Approval policy: the auto-factory-approval-mode / -risk-threshold / -approval-gates flags compile into pre-execution gates. A gated step halts the chain BEFORE it runs; adding the PR label af-approve:<step> resumes it. Yolo (the default) means no gates.
  • Knowledge graph (auto-factory-knowledge-graph flag, off by default): the run composes an impact graph from LaunchDarkly-native sources — service→service edges derived from observability traces, flag→code wrap points from an ld-find-code-refs dry-run at the PR SHA, and changed-file→service mapping from the repo's .autofactory/services.yaml. Every source is fail-soft: missing telemetry or a missing scanner binary becomes a warning + a gaps entry, never a failed run.
→
Step 3
Research & Planner
read-only analysis
Sonnet — reasoning
Tools: git_diff, file reads, grep; its only write is the release manifest (write_manifest). No code edits.
  • Classifies pr_type, risk_level, change_scope, change_patterns, user-facing impact.
  • Records the repo's existing flag, test, and telemetry patterns; downstream agents match them.
  • Flag landscape research (get_flag_state): for every flag already gating touched code, reads its kind, variation lineage (control/v1/v2…), and per-environment RELEASED-ness — then decides the flag_action: create | ride_existing (unreleased variation — amend it) | extend_variation (released — mint vN+1) | child_flag (net-new inside flagged code, or a released legacy boolean) | none.
  • Creates the release manifest .release-flags/pr-N.json via write_manifest, including the human-editable releaseIntent skeleton — so an approver at a gate has a form to fill in BEFORE implementation.
  • Routing: tags flag_worthy and a numeric risk_score (0–1, consumed by the risk-threshold approval mode). Tagging skip_flagging=true ends the chain (config-only, docs, dependency PRs).
  • When the knowledge graph is on, it also gets query_dependencies: a no-argument call returns this PR's blast radius (changed services, dependent services with evidence, upstream contracts, flags already wrapping the changed code). Graph gaps are reported as UNKNOWN coverage, never as low risk — a thin graph can't launder a risky change.
→
⛊
Brief verified — deterministic shim (no model): the release manifest is written only through write_manifest, which validates machine fields mechanically (real flag keys in prerequisites, vN-only targetVariation) and rejects prose; required routing tags (flag_worthy, flag_action, risk_score) are FORCED if the agent forgets — risk gates fail closed without them.
→
Step 4
Manifest Steward
normalizes human release intent
Sonnet — reasoning
Sits exactly where human edits land: after research (and any approval gate), before implementation.
  • Reads the manifest's releaseIntent block — the human's stated intent ("hold", "release after Aug 1", "child of flag-xyz", a beta segment) typed at the approval gate.
  • Promotes free-text notes into structured fields (e.g. a note naming a parent flag becomes prerequisites) via one write_manifest call. Only the steward capability may UPDATE intent; other agents can only create the skeleton — a re-run can never clobber what a human typed.
  • Never broadens intent (never hold→auto). Fast no-op when the skeleton is untouched. A deterministic normalizer in Beacon backstops it: unintelligible intent fails closed to hold.
  • Passes the research brief through unchanged.
→
⛊
Intent fail-closed — deterministic shim (no model): a deterministic normalizer re-parses releaseIntent on every read (here and again in Beacon at deploy time): unknown actions, unparseable dates, or a malformed block fail CLOSED to hold — an unintelligible human intent can never be read as “release it”.
→
Step 5
Flag Implementer
creates the flag, wires the code
Composer ⇄ Sonnet (A/B)
⚖ judged
Executes the research planner's flag_action — it does not re-decide.
  • create/child_flag: creates a STRING MULTIVARIATE flag (control + v1, targeting off everywhere; never boolean — only multivariate flags can take iteration variations later). Child flags attach the parent as a prerequisite: armed on-behind-parent while the prerequisite is unmet, left dark when the parent already serves it.
  • extend_variation: appends vN to the existing flag (add_variation) and wires the PR's changes under it — dark until released; the previous variation's path stays intact.
  • ride_existing: no LaunchDarkly change — use_existing_flag VERIFIES the ridden variation is genuinely unreleased (refuses live ones) so the chain can advance honestly.
  • Wires string comparisons with fail-safe default 'control'. The control path keeps prior behavior exactly.
  • Corrects the manifest's flagKey/targetVariation via write_manifest (the intent block is preserved).
  • Commits to the PR branch. Re-runs are idempotent: 409s reuse the flag; add_variation reuses the intended value.
  • An attached LaunchDarkly judge (implementation-quality) then scores the output 0..1 against the agent's actual git diff (pipeline-gathered evidence, not the agent's claims). Non-blocking; scores record per-variation for the model A/B.
→
⛊
Flag verified — deterministic shim (no model): the chain advances only on the tool-owned flag_ready tag — set by the flag tools from the actual LaunchDarkly API response and STRIPPED from any agent claim. The handoff shim then re-derives the claim from primary evidence: the flag and its claimed variation exist in LaunchDarkly (fresh read), the flag key is referenced in the code, and the vN variation is compared (quoted) in a file evaluating it — a multivariate flag wired through a boolean helper fails here mechanically. Any failed check halts the chain.
→
Step 6
Metrics Author
creates guarded-release metrics
Composer ⇄ Sonnet (A/B)
⚖ judged
  • Metric categories: error (occurrence, lower is better), latency (numeric ms, lower is better), business (occurrence, higher is better).
  • Sentry estate (ADR 0015, optional sentry variation): when LD targeting serves the metrics author's sentry variation and Sentry creds/env are present, call query_sentry early for an estate picture (top issues, error volume, launchdarklyContext coverage, dual-export hints). Guardrails remain LD metrics — never invent latency killswitches from Sentry Explore aggregates alone.
  • Sentry error path (ADR 0014, sentry variation): prefer shared sentry-errors-binary / sentry-errors-count (LD↔Sentry integration event key sentry-errors) as the error killswitch; instrument Sentry custom context named exactly launchdarklyContext; tag sentry_guardrail=true. For latency prefer existing otel* via list_metrics when dual-export/LD o11y is present; else feature-scoped track() / document the dual-export gap.
  • Otherwise adds track() calls on the flagged path. Telemetry is wrapped so a tracking failure cannot fail the request.
  • Creates each feature-scoped metric with eventKey equal to the tracked event name. Metric key convention: <flag>-<category>.
  • The metric randomization unit must equal the flag rollout unit (default user).
  • Metric backing rules: guardrails must be per-unit attributable — track() events (default), Sentry→LD error metrics, or trace metrics on span attributes (flag evaluated inside the active span). Pre-aggregated OTel metrics never qualify.
  • Telemetry footprint (M10): when the service already uses the LaunchDarkly observability SDK, the agent span-covers the flagged path (flag evaluated in-span, <flag>.<attribute> span attributes) — growing the very telemetry the knowledge graph reads. Each processed PR widens the map that informs the next PR.
  • Classifies metrics killswitch / pause / monitoring and writes metricKeys + randomizationUnit into the manifest.
  • An attached LaunchDarkly judge (metrics-quality) then scores the output 0..1 against the agent's actual git diff (instrumentation + manifest edits). Non-blocking; scores record per-variation for the model A/B.
→
⛊
Metrics verified — deterministic shim (no model): metric tags (metrics_created, metric_keys, metric_event_keys) are tool-owned — they derive from LaunchDarkly API responses. The shim then greps the checkout for an EMITTER of every event-backed metric’s event key (Sentry integration key sentry-errors exempt). When sentry_guardrail=true, also requires launchdarklyContext in the checkout.
→
Step 7
Flag Testing
flag-on and flag-off tests
Composer ⇄ Sonnet (A/B)
  • Writes variation-path tests per flagged path: the PR's variation asserts the new behavior, control asserts the prior behavior — and on an extend_variation PR, vN-1 keeps ITS behavior too (three-way coverage).
  • Uses the repo's existing test framework and conventions.
  • Executes the suite (run_tests) and fixes failures before committing.
→
⛊
Tests executed — deterministic shim (no model): run_tests executes the suite for real (deps installed, pytest/npm/go), and the tool records the LAST run’s outcome as the tool-owned tests_last_run tag. Handing off with a red suite fails the run mechanically — “the tests pass” is an execution result, never an agent claim.
→
Step 8
Code Reviewer
APPROVE / REJECT + risk_level
Sonnet — reasoning
Read-only review of the full diff, including the agents' commits.
  • Checks logic, error handling, control-path preservation, and test quality.
  • Validates instrumentation: track() event names are checked against each metric's event_key, not against metric keys.
  • Tags review_approved and risk_level — the at-a-glance verdict on the PR (a rejection fails the check run). Human approval itself happens earlier, at the pre-execution gates.
→
⛊
Verdict read mechanically — deterministic shim (no model): the check-run verdict is computed from tags alone (interpretWalk): tool-owned tags can’t be faked, a missing reviewer verdict reads as INCOMPLETE (never as approval), a chain stall or failed shim is reported as exactly that, and the GitHub check goes green only on an approved (or verified no-op) walk.
→
Step 9
Human merges
flag remains off
Standard merge. The flag is off in every environment, so the deploy serves the control path. The release manifest is now on the default branch where Phase 2 discovery can see it.

Phase 2: deploy → guarded release (Beacon)

HTTP service, hosted separately from the application. Receives deploy notifications, diffs release manifests, and triggers releases via the LaunchDarkly API. The release itself — traffic shifting, metric monitoring, auto-rollback — runs server-side in LaunchDarkly; Beacon only observes the outcome.

Step 10
CD deploys the services
existing deploy pipeline
The merge deploys through the team's existing CD (Railway in the demo, via its GitHub integration). AutoFactory does not run the deploy; it only consumes a notification that a deploy succeeded.
→
Step 11
Deploy webhook → Beacon
POST {service, sha} + secret
Generic endpoint /flag-releases accepts {service, sha, previousSha?, environment?}, authenticated by a shared secret in a header or query parameter.
  • Provider adapters translate native payloads to the same handler. The Railway adapter reads details.status, details.commitHash, resource.service.name.
  • Only success statuses proceed. Other deploy statuses return 200 with ignored.
  • Providers retry non-2xx deliveries, so all handling is idempotent.
→
Step 12
SHA diff → discovery
previousSha resolution + manifest diff
.release-flags/ is listed at the deployed SHA and at the previous SHA (GitHub contents API). Manifests present only at the new SHA are released.
  • previousSha resolution order: explicit field in the notification, then Beacon's deploy-state store (last SHA per service@environment), else none. With none, all current manifests are treated as new (first deploy).
  • The store keeps last and prior SHAs. Re-delivery of the current SHA re-diffs prior..sha instead of the empty sha..sha.
  • No dependency on the CD system reporting its own deploy history.
→
Step 13
Scope & fullstack check
frontend / backend / fullstack
Each manifest carries a scope; each service registers a side (config/services.yaml).
  • A notification from the wrong side skips the flag; the right side's notification releases it.
  • Fullstack: Beacon reads the other side's status endpoint for its deployed SHA and checks that SHA contains the same manifest file. If absent, the flag waits and is re-evaluated when the other service's notification arrives.
→
Step 14
Release trigger
method and stages by precedence
  • Human releaseIntent is honored FIRST: hold/manual and future notBefore dates hold the release (with the reason recorded); prerequisites wire LD-native flag prerequisites instead of an automated release. Unintelligible intent fails closed to hold.
  • Then method precedence: manifest releasePlan.releaseMethod (legacy releaseOverrides still read), then the flag's configured release policy, else guarded when metricKeys exist, progressive otherwise.
  • Stage precedence: overrides, then policy, then defaults (guarded 20%/50%, progressive 20/50/100%).
  • Guarded stage allocations are limited to 50% by the API; the release serves 100% after the final stage completes.
  • Multivariate flags release a VARIATION: target = the manifest's targetVariation (else the lineage tip), original = whatever the environment serves today — a first release moves control→v1; an iteration release moves v1→v2 on an already-on flag. Already serving the target is an explicit noop.
  • Fresh flags are off, so the semantic patch combines turnFlagOn and startAutomatedRelease in one request.
  • A flag with an in-progress release reports already_running instead of re-triggering.
  • After a variation release completes, Beacon re-points auto-factory child flags whose prerequisite pins the parent's PREVIOUS variation (LD prerequisites pin a variationId; without this, releasing v2 would silently darken children pinned on v1). Hand-built dependencies are surfaced, never rewritten.
→
Step 15
LaunchDarkly runs the release
staged rollout, metric monitoring — server-side
From here the work is LaunchDarkly's, not Beacon's: LaunchDarkly shifts traffic per stage and continuously compares the Phase 1 metrics between treatment and control on live traffic.
  • autoRollback is set per metric at trigger time.
  • The randomization unit from the manifest keeps measurement aligned with the rollout.
  • No Beacon involvement: the release progresses (or reverts) even if Beacon goes down.
→
Step 16
Beacon observes
status polling + outcome record only
Beacon resolves the release id (per-flag automated-releases list, filtered to in_progress) and polls purely to RECORD the outcome — it takes no release actions:
  • completed: rolled out to 100%.
  • reverted: LaunchDarkly's guardrail monitoring regressed a metric and returned traffic to control.
  • monitoring_stopped: a human intervened.
  • Polling runs detached from the webhook request. A Beacon failure has no effect on the release, which LaunchDarkly runs server-side.
→
On regression
Auto-rollback (LaunchDarkly)
flag reverts to control, server-side
LaunchDarkly's guarded release detects the killswitch metric regression and reverts: traffic returns to the ORIGINAL variation by flag change — control on a first release, the previous vN-1 on an iteration release (v2 regresses back to v1, not to off) — with no deploy and no Beacon involvement. Beacon records the reverted terminal state and, when BEACON_SEER_AUTOFIX is on, starts Seer Autofix on a matching Sentry issue (ADR 0014 / shared matcher ADR 0015).
